IP routing explainer

How anycast works

Anycast means giving the same IP address to servers in many places and letting the Internet's routing deliver each packet to whichever one is closest to the sender.

You already know the unicast picture: one address names one host, and a UDP datagram addressed to it ends up at that host. Anycast keeps everything about the packet the same and changes only the assumption that an address lives in one place.

One address, many locations

With unicast, every client on Earth sends to the same machine, however far away it is. With anycast, several sites all claim the address. Each client's packets reach one of them, usually a nearby one, and the client cannot tell the difference.

Nothing in the packet marks it as anycast. The IP header and the UDP header are byte for byte what they would be for a unicast destination. There is no special address range and no flag. Anycast exists entirely in how routers have been told to reach that address.

The mechanism is BGP

The Internet is a mesh of independently run networks called autonomous systems (ASes). They tell each other which address blocks they can reach using BGP. An announcement says, in effect, "send traffic for 198.51.100.0/24 my way", and each network passes it on to its neighbours with its own AS number added to the path.

Normally one site announces a given prefix. To anycast it, you announce the same prefix from every site. Routers elsewhere now hear several routes to one destination. That is routine for BGP, which always hears multiple paths and keeps the one it prefers. Each router then forwards packets along its own best route, with no idea that different routers' best routes end at different machines.

Try it. Pick a client to trace its path, and withdraw a site's announcement to see the network re-converge.

What "closest" means

Closest is measured by routing preference, and geography only correlates with it. A BGP router compares candidate routes roughly in this order:

  1. Local policy. Operators rank routes by business relationship first. A route through a customer or a free peering link usually beats one through a paid transit provider, whatever its length.
  2. AS path length. Fewer networks to cross wins. This is the hop count the diagram uses.
  3. Tie-breakers. Among equal routes, the router prefers the exit that is cheapest to reach inside its own network.

The result tracks physical distance well enough to be useful, but a client can be sent to a site on another continent because its ISP's cheapest path happens to lead there. Anycast operators spend real effort measuring catchments and tuning announcements to fix cases like that.

What happens to a UDP exchange

Take a DNS query to an anycast resolver. On the wire it looks like any UDP request and response:

# client to service: routed by anycast, lands at the nearest site
203.0.113.7:53124  →  198.51.100.1:53     query

# service to client: ordinary unicast back to the client's own address
198.51.100.1:53    →  203.0.113.7:53124   answer

Two details matter here.

  • The reply must come from the anycast address. The client matches the answer to its socket by source address and port, so the site answers as 198.51.100.1 even though the machine also has a private unicast address of its own. A server listening on a wildcard UDP socket has to take care to reply from the address the query arrived on (for example with IP_PKTINFO), or the kernel may pick a different source.
  • Only the inbound direction is anycast. The client's address is unique, so the reply takes a normal unicast route. The two directions can cross different networks.

The same asymmetry explains why sites never originate conversations from the anycast address. If Site 1 sent a request with source 198.51.100.1, the response would go to whichever site is nearest the responder, which may be Site 2. Each machine keeps a unique unicast address for its own outbound traffic and for management.

Why stateless UDP services fit so well

Routes shift now and then: a link fails, an operator changes policy, a site is withdrawn. When that happens, a client's next packet may land at a different site from its last one. Whether that hurts depends on whether the sites need to remember anything about the client.

A DNS lookup is one datagram each way, and every site can answer it identically, so anycast and DNS over UDP suit each other perfectly. Protocols that build sessions on top of UDP, such as QUIC, inherit the TCP problem because the session state again lives at one site.

In practice, routes on the Internet are stable for hours or days, far longer than most connections last. That is why CDNs run TCP and QUIC over anycast at enormous scale. Routers also keep each flow on one path when several are equally good, by hashing the address and port tuple, so packets of one connection do not get sprayed across sites.

Failure and withdrawal

Withdrawing Site 1 in the diagram above shows anycast's failover. The site stops announcing the prefix, its neighbours drop that route and tell their neighbours, and within seconds to a few minutes every router has settled on the next-best site. Clients do nothing. They keep sending to the same address.

The catch is that BGP only knows whether the announcement is present. A site whose service has crashed but whose router is still announcing becomes a black hole for its whole catchment. Every anycast deployment therefore ties the announcement to a health check: if the service stops answering, the site withdraws its own route.

Operators use the same lever on purpose. To drain a site for maintenance they withdraw the prefix there, wait for traffic to move, and do the work.

Where it is used, and what it costs

Good at

  • Latency. Clients reach a nearby site with no lookup step and no client logic.
  • Resilience. A site can vanish and its clients are rerouted by the network itself.
  • Absorbing floods. Attack traffic is split by where it originates, so each site faces only its own catchment's share.
  • One address to configure. This is why public resolvers can hand out memorable addresses such as 1.1.1.1, 8.8.8.8 and 9.9.9.9, and why the DNS root can run on 13 named server addresses backed by well over a thousand machines worldwide.

Trade-offs

  • No direct control. Other networks' policies decide which site a client reaches. You can nudge catchments but cannot assign clients.
  • Uneven load. Catchments follow topology, so one site may get most of the traffic.
  • Harder debugging. "The server" is a different machine depending on where you ask from. Operators expose an identity query for this, such as dig CH TXT id.server @1.1.1.1.
  • Stray ICMP. Error messages addressed to the anycast address, such as "packet too big", can land at a different site from the one that sent the original packet.
  • Address cost. Networks generally ignore announcements smaller than a /24 in IPv4 or a /48 in IPv6, so an anycast service needs a whole block of that size.

The short version

  • An anycast address is an ordinary address announced from several places at once.
  • BGP routers each pick their preferred route, so packets drain toward the topologically nearest site.
  • The client sends plain unicast-looking UDP and gets a reply from the same address. It never learns which site answered.
  • Stateless request and response protocols are unaffected by route changes. Connection-oriented ones can be reset by them, which is rare enough in practice to be acceptable.
  • Failover is a route withdrawal, and it only works if the announcement tracks the health of the service.
